Projet IA — de votre PC à la production

Chez vous, vous avez souvent une machine plus puissante qu'au lycée. En deux séances, chacun conçoit une petite application qui s'appuie sur un modèle de langage qui tourne sur son propre PC, la met en production derrière une adresse publique en HTTPS, la mesure et la sécurise. Concevoir, piloter, mesurer, sécuriser : les quatre se voient dans le rendu.

À chaque séance, en arrivant

  1. Ouvrez le portail, identifiez-vous, répondez à la question du jour : c'est votre présence, l'appel Pronote en est tiré.
  2. Carte « Vos missions » : séance 21 le lundi, séance 22 le mardi. Cochez une mission quand elle est faite et poussée sur GitHub.
  3. Pas de visio. Bloqué plus de 15 minutes ? Messagerie Pronote, avec le message d'erreur copié et la commande qui l'a produit : je réponds pendant les deux heures.

Si possible avant lundi : installez Ollama et Docker Desktop, ce sont les deux téléchargements les plus longs. Sans ordinateur utilisable chez vous, écrivez-moi avant lundi 9 h : une solution de repli existe.

Les exigences communes

Quel que soit le sujet, le projet rendu doit tenir les sept :

  1. Le modèle tourne en local avec Ollama, choisi selon votre carte graphique (tableau ci-dessous).
  2. Une application web (le kit de départ, ou l'équivalent dans un autre langage) conteneurisée et lancée par docker compose, avec redémarrage automatique et vérification de santé.
  3. Une URL publique en HTTPS par un tunnel sortant : aucun port ouvert sur votre box.
  4. Un code d'accès, une limite de requêtes et une taille d'entrée bornée : votre PC n'est pas à la disposition de tout Internet.
  5. Ollama n'est jamais exposé : seule l'application parle au modèle.
  6. 10 cas d'évaluation au moins, deux modèles comparés, trois essais par cas.
  7. Un dépôt GitHub personnel avec le README.md rempli, et aucun secret commité (.env reste chez vous).

Lundi 5 octobre — séance 21 : concevoir et faire marcher

1 Votre machine et votre modèle Concevoir · 25 min

  1. Relevez carte graphique, VRAM et mémoire vive ; choisissez votre modèle dans le tableau.
  2. Téléchargez-le et essayez-le : 
    ollama pull qwen2.5:3b
ollama run qwen2.5:3b --verbose
    Posez deux questions. --verbose affiche la vitesse (eval rate, en tokens par seconde) : notez-la.
  3. Vérifiez où tourne le modèle : ollama ps indique la part GPU et la part CPU.
Indice — « ollama » n'est pas reconnu

Ollama tourne en arrière-plan après son installation (icône près de l'horloge sous Windows). Fermez puis rouvrez le terminal pour qu'il trouve la commande.

2 Le sujet et le dépôt Concevoir · 20 min

  1. Sur BTS2-Projet-IA, Use this template : créez votre dépôt personnel projet-ia-<prenom>, clonez-le, et après chaque git push vérifiez sur GitHub que .env n'y est pas.
  2. Choisissez votre sujet. Dans le README.md de votre dépôt, remplissez §1 Concevoir (besoin, trois cas d'usage, deux limites) et §2 (machine et modèle).

3 Votre application, en local Construire · 45 min

  1. Écrivez prompt.txt pour votre sujet : rôle, tâche, règles, format de sortie avec un exemple. Adaptez le titre et la phrase de static/index.html.
  2. Lancez l'application sans Docker, pour aller vite : 
    python -m venv .venv
.venv\Scripts\activate          (macOS / Linux : source .venv/bin/activate)
pip install -r requirements.txt
copy .env.example .env          (macOS / Linux : cp .env.example .env)
    Dans .env, mettez OLLAMA_URL=http://localhost:11434, votre modèle et un code d'accès d'au moins 8 caractères. Puis : 
    uvicorn main:app --env-file .env --reload
    et ouvrez http://localhost:8000.
  3. Essayez cinq demandes réalistes. Retouchez prompt.txt jusqu'à ce que le format de sortie soit tenu. Commitez.
Indice — sortie JSON

Pour les sujets 2 et 3 : donnez dans prompt.txt un exemple complet de JSON attendu, et demandez « réponds uniquement par ce JSON ». Ollama accepte aussi "format": "json" dans le corps de la requête : cherchez où l'ajouter dans main.py.

Indice — sujet 1, le texte de référence

Un règlement de deux pages tient dans la consigne : collez-le à la fin de prompt.txt entre deux balises, et demandez au modèle de ne répondre qu'à partir de ce texte. Pour un texte bien plus long, il faudrait une recherche par similarité (RAG) : c'est un bonus, pas une exigence.

4 Le jeu d'évaluation Mesurer · 25 min

  1. Dans cas.json, écrivez 10 cas au moins : sept demandes normales variées, deux hors sujet, une qui tente de faire ignorer les consignes. Pour chacun, ce que la réponse doit et ne doit pas contenir.
  2. Premier passage : 
    python evaluer.py http://localhost:8000 VOTRE_CODE
  3. Notez le taux et le temps médian dans le README (§4), remplissez la ligne du lundi au §3, commitez et poussez.

Un cas qui réussit toujours ne mesure rien. Gardez au moins deux cas difficiles.

Mardi 6 octobre — séance 22 : mettre en production et mesurer

1 Conteneuriser Piloter · 30 min

  1. Dans .env, remettez OLLAMA_URL=http://host.docker.internal:11434 (Ollama installé sur le PC). Sous Linux, suivez plutôt l'option B décrite en tête de compose.yaml.
  2. Lancez : 
    docker compose up -d --build
docker compose ps
    L'application doit passer à healthy. Sinon : docker compose logs app.
  3. Prouvez le redémarrage automatique : docker compose restart app, puis attendez qu'elle repasse healthy.

2 L'URL publique Piloter · 20 min

  1. Le service tunnel démarre avec l'application. Votre adresse publique est dans son journal : 
    docker compose logs tunnel
    Elle ressemble à https://mots-au-hasard.trycloudflare.com.
  2. Testez-la depuis votre téléphone, en 4G (pas sur votre wifi) : sans le code, l'application refuse ; avec, elle répond.
  3. Notez-la en tête du README.
Pourquoi un tunnel ? Il part de votre PC vers Cloudflare : rien n'est ouvert sur votre box, et seule l'application (port 8000) est joignable. Ce type d'adresse est gratuit mais change à chaque redémarrage du tunnel : si elle change, mettez à jour votre rendu. Quand vous avez fini d'être évalué, arrêtez tout avec docker compose down.

3 Mesurer et comparer Mesurer · 30 min

  1. Rejouez votre jeu sur l'URL publique, trois essais par cas : 
    python evaluer.py https://….trycloudflare.com VOTRE_CODE --essais 3
  2. Changez MODELE dans .env pour le modèle de comparaison (ollama pull d'abord), relancez docker compose up -d, rejouez.
  3. Remplissez le tableau du §4 et commentez deux échecs : pourquoi le modèle s'est trompé, et ce que vous avez changé (consigne, modèle, température…).

La limite de requêtes s'applique aussi à vous : avec 10 cas × 3 essais, passez REQUETES_PAR_MINUTE à 40 le temps de la mesure, puis remettez 10.

4 Sécuriser Sécuriser · 20 min

  1. Remplissez le tableau des risques du §5 : pour chaque ligne, ce qui pourrait arriver et la mesure qui est dans votre projet (fichier et ligne).
  2. Vérifiez, et collez la preuve dans le README :
    • docker compose ps : seul 127.0.0.1:8000 est publié, le port 11434 n'apparaît pas ;
    • git log --all --oneline -- .env ne renvoie rien ;
    • votre cas « ignore les consignes » est bien refusé.

5 Rendre 15 min

  1. README complet (§1 à §7), dernier commit poussé.
  2. Dans le travail à faire Pronote du mardi, déposez un texte avec : l'adresse du dépôt GitHub (invitez ggaillard s'il est privé), l'URL publique et le code d'accès.
  3. Laissez l'application en ligne jusqu'à mardi 20 h : je la teste à ce moment-là. Faites l'auto-évaluation au portail.
